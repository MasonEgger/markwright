## Project Overview

markwright is a set of Python-Markdown extensions plus an `mw` command-line tool. Part of it is a port: eight of the fifteen extensions (highlight, fence, youtube, codepen, twitter, instagram, slideshow, image_compare) reproduce the syntax and HTML output of DigitalOcean's [`do-markdownit`](https://github.com/digitalocean/do-markdownit) (JavaScript/markdown-it, Apache 2.0); the other seven, the config system, and the CLI are markwright's own. The `mw` tool exposes the same extensions as pre/post filter stages so the syntax works in any toolchain (Hugo, a plain Unix pipe, etc.), not only an in-process Python-Markdown render. The bundled MkDocs Material site in `docs/` is both documentation and a live demo. Scope rule: markwright owns syntax that no maintained Python-Markdown or pymdown-extensions extension provides, plus block-level features the `mw` pipeline needs because Hugo has no equivalent (tabs is the one such feature so far); it does not reimplement what the base renderer already provides. The upstream name `do-markdownit` appears in attribution (NOTICE, README) and must be preserved; the package and the CLI use the `markwright` / `mw` brand. Runtime dependencies are `markdown`, `pymdown-extensions` (floor set by a security fix), and `pydantic`.

CI (GitHub Actions, `ci.yml`) runs on push and PR to main and monthly: one `check` job per Python 3.11 through 3.15 that installs a pinned Hugo and runs `just check` (plus `pip-audit` once), then `deploy` (docs to GitHub Pages, push to main only, the only job with write permission). `workflow.yml` publishes to PyPI via trusted publishing when a GitHub Release is published, after the same audit and gate. Dependabot updates `uv.lock` (lock file only, so it never raises a floor in `pyproject.toml`) and Actions weekly. The `gh-pages` branch is auto-managed build output, force-pushed by `mkdocs gh-deploy`; never commit to it, merge it, or delete it.

## Architecture

The codebase has **two consumers over one set of pure stage functions**, so the extension logic is written once and used by both the in-process Python-Markdown render and the CLI.

**Pure stage functions (per extension module):**

- `expand_source(text: str, options: Mapping[str, object] | None = None) -> str` is the source stage (`mw pre`): expands embed directives to raw HTML, extracts fence directives into a marker comment, and (highlight) wraps prose `<^>` runs. Fence reads `options` (its `allowed_environments`) and the four third-party embeds read `load`; the others accept and ignore it so the registry can call every pre function with one signature.
- `apply_html(rendered_html: str, skip_reasons: list[str] | None = None, options: Mapping[str, object] | None = None) -> str` is the HTML stage (`mw post`): applies fence styling, wraps in-code highlight markers, injects embed scripts. Only fence uses `skip_reasons` and `options` (its label classes); the others accept and ignore them.

**In-process adapters.** The Python-Markdown `Extension`/`Preprocessor`/`Postprocessor` classes are thin adapters that delegate to the stage functions. Embed preprocessors stash raw HTML via `self.md.htmlStash.store(...)` (so Markdown does not re-parse it and break JS backticks or wrap blocks in `<p>`); the `expand_source` path emits the HTML inline for the CLI. Both go through a per-extension `_render_match(line) -> str | None` helper (`_render_match(line, load)` for the embeds that take `load`). Extensions are loaded by name, e.g. `markwright.highlight`.

**Parsing structured text.** Three private modules own it, so no stage parses Markdown structure or HTML with ad hoc regex:

- `_fences.py` finds fenced code blocks by CommonMark's rules (0 to 3 column indent, or under a list item or in a block opener's body, a tab counting as four columns, closing fence of the same character and at least the opening length, unclosed fences are not code).
  It also finds top-level indented code blocks (four columns after a blank line, not list content and not the body of an admonition, details, content-tab, definition, or footnote opener), which `map_prose` and `map_lines` skip.
  One forward pass (`_scan_blocks`) classifies every line's block context, and the result is cached per document (`_code_regions`) so successive pre stages over unchanged text share it.
  `map_prose(skip_inline_code=False)` leaves inline code spans inside the runs it hands the transform; only highlight turns the skip off.
  `map_prose(skip_blocks_opened_by=...)` also skips the blocks one stage emitted, from a line starting with that open tag through the first `</pre>` after it (text after it on that line is prose); only icons turns it on.
  Fence's directive extraction and highlight's prose pass both use it, which is what keeps the two pre stages in parity.
- `_containers.py` is the container-pairing scanner (`scan_containers`) shared by grid and tabs.
  It walks the lines outside fenced and indented code (through `_fences`) with a stack and pairs each `[/grid]`, `[/card]`, or `[/tab]` closer with the nearest unpaired opener of its kind at the same indentation column (a tab counts to the next stop of four, and a non-blank line indented less than an opener ends that container unclosed, so a container never straddles two list items; a card counts as inside a grid only when that grid pairs), returning matched pairs, unpaired-or-misplaced problems, and unclosed `[grid]` shortcuts.
  It recognizes a stage's own emitted marker-comment lines (`mw-grid-block`, `mw-card`, `mw-tab`, and their `-end` closers) as openers and closers and flags those results `from_marker`, so the owning stage skips its own markers and pairing survives `mw pre` run twice over its own output.
- `_html.py` tokenizes rendered HTML with the stdlib `html.parser` and keeps each token's source offsets (`HtmlToken`). Post stages find elements from tokens and apply span edits (`apply_edits`), so everything they do not touch stays byte-identical. A tree parser (lxml, selectolax) would re-serialize the whole page and is deliberately not used. `provider_script_needed` decides script injection from parsed classes and `src` attributes.

- `_markers.py` owns the versioned `<!-- NAME:{JSON} -->` marker comment (`encode_marker`, `find_markers`, `decode_marker`) that carries data from a pre stage to a post stage, plus `marker_block` (a marker comment emitted as its own indented block, blank lines around it), `match_marker_pairs` (stack-match open and close markers by position), `inline_problem_marker` (append a problem marker to a literal line), and `report_problem_markers` (compose one `--warn` message per problem marker). It is fail-soft on read and comment-safe on write (`<`, `>`, and the backtick are `\uXXXX`-escaped). Fence, grid, annotate, and tabs share it, so the contract lives in one place.

Regex remains for single-line token grammars (the `[youtube ...]`-style directive lines ported from do-markdownit, fence info strings, the marker comment's own format, inline code spans, which highlight reads across a line end but never a blank line, and `<^>` markers within known text).

**Config.** `config.py` owns the tuning surface: `load_config(explicit_path, start_dir) -> Config` discovers a standalone `markwright.toml` or a `[tool.markwright]` table in `pyproject.toml` by walking up with `pathlib`, parses it with stdlib `tomllib`, and validates it fail-loud into a frozen pydantic `Config` (a boundary `ConfigError`, never a traceback). `Config` carries the selection intent (`enable`/`disable`), per-extension option tables, the `warn` default, and a source map for `mw config`. It depends on `registry` (`EXTENSION_NAMES`, `OPTION_NAMES`, `REGISTRY`), `_diagnostics` (`ConfigWarning`, `OptionError`), and `fence` (the environment scan behind `disallowed_environments`), and nothing else; `fence` never imports `config`, so keep that direction. It drops `None` values (omitted), rejects option keys outside `OPTION_NAMES`, and runs each `StageSpec.check_options` (the extension's own reader), wrapping its `OptionError` (a `ValueError` subclass in `_diagnostics.py`) in a `ConfigError`; any other exception from a checker is a bug and propagates.

**Public host API.** `config.py` also exposes the API host tools (first consumer: Bartleby) build on, re-exported from the package root: `config_from_mapping(table, source)` validates an already-parsed table with the same rules as a file (errors prefixed with the `source` label, `source_path` left `None`; a table that is not a mapping is a `ConfigError`, `None` is an empty table, and an unknown key is an error whatever its value), `selected_extensions(config)` applies `enable`/`disable` (an empty selection emits a `ConfigWarning`, never an error), `extension_configs(config, names)` builds `markwright.<name>` option dicts for `markdown.Markdown`, and `disallowed_environments(source, config)` lists the fence environments a document names outside `fence.allowed_environments` (the scan lives in `fence.environment_names`, and neither it nor the option and selection reads warn). `mw render` uses these same functions; only `--exclude` and the `pymdownx.highlight` entry stay CLI-side.

**Registry and CLI.** `registry.py` maps each extension name to a frozen pydantic `StageSpec` (`pre`, optional `post`, priorities, the Python-Markdown `extension` class, optional `check_options`) and provides `run_pre`, `run_post` (each threads every extension its option dict from config), and `describe`. `OPTION_NAMES` derives each extension's accepted keys from its class's declared `config`, so a new option is declared once. `cli.py` is a stdlib `argparse` CLI (`main(argv) -> int`) with subcommands `pre`, `post`, `render`, `config`, and `list`; the entry point is `mw = markwright.cli:main`. Selection resolves from config with `--exclude` (argparse `choices`) applied last via `_resolve`. `main` sets UTF-8 on stdin and stdout, and `mw pre` splits a leading YAML (`---`) or TOML (`+++`) front matter block off and writes it back untouched. Helpers raise; `main` is the only place exceptions become exit codes (`ConfigError`, an icons `OptionError`, a `ConfigWarning` escalated by `-W error`, or a stdin or stdout failure such as a decode error, closed stream, or broken pipe, prints one `mw: error:` line and returns 2), because library code raises and only the CLI boundary returns codes. `render` builds a `markdown.Markdown` with `pymdownx.superfences` + `pymdownx.highlight` + the selected extensions and their config. `config` prints the resolved configuration and the source of each value.

### The Extension Patterns

1. **Fence** (`fence.py`): `expand_source` extracts directives (`[label]`, `[secondary_label]`, `[environment]`) and prefix flags (`line_numbers`, `command`, `super_user`, `custom_prefix(...)`) and emits one `<!-- mw-fence:{JSON} -->` comment before the fence (at the fence's indentation, plus a blank line when indented, so it stays inside a list item), keeping the fence so the renderer still highlights it. `apply_html` validates each marker with the strict pydantic `FenceMarker` (unknown fields ignored), then applies label divs, environment classes, and `<ol><li data-prefix>` wrapping to the first `<pre>`/`<code>` before the next marker. The marker is a cross-tool contract: it carries `"version": 1` and is read fail-soft (malformed JSON, a non-object payload, an unsupported version, a wrongly typed field, or no following block is skipped and reported under `--warn`). Line-prefix wrapping handles two renderers: Pygments emits flat newline-delimited lines, while Chroma (Hugo) wraps each line in `<span class="line">`, which are taken whole from the tokens.

2. **Embeds** (youtube, slideshow, image_compare, codepen, twitter, instagram): `expand_source` replaces standalone `[name ...]` lines with raw HTML, through `_fences.map_directive_lines`, which starts every line of the expansion at the directive line's indentation so it stays inside a list item or a block opener's body (the stash placeholder in-process is indented the same way). Flag parsing lives on pydantic settings models (`CodePenSettings.from_flags` and friends). The script embeds (codepen, twitter, instagram) also have `apply_html`, which appends the provider `<script>` once when `_html.provider_script_needed` finds an embed element outside every `<template>` and no script with that `src`. This is idempotent and shared by the in-process postprocessor and the CLI.

   **Load modes.** youtube (`eager|lazy|click`) and codepen, twitter, instagram (`eager|click`) take a `load` option, declared in each `Extension.config` (Python-Markdown raises `KeyError` on undeclared keys) and read by `expand_source` from `options`. `eager` output for a directive at column 0 must stay byte-identical to earlier releases (an indented directive's expansion keeps the line's indentation). `click` wraps the eager markup in the versioned `mw-embed` preview (`data-mw-version="1"`, live markup in `<template class="mw-embed-content">`), documented in `docs/click-to-load.md` as a public contract like the fence marker. `_embed_load.py` holds `load_mode`, `wrap_preview`, and the shared URL-prefix grammar.

3. **Highlight** (`highlight.py`): keeps an InlineProcessor for in-process prose; it matches an opener alone and takes the next marker on the same line as the closer, so a pair never holds a line end, and an opener with no closer there, or a pair whose text holds a stashed block's placeholder, stays literal. `apply_html` reads escaped `&lt;^&gt;` markers and their backslash escapes from the text tokens joined with the tags taken out (never attributes, `<script>`, `<style>`, `<title>`, or `<textarea>`), so a highlighter's `<span>` between a backslash and a marker, or inside the marker, changes nothing; it pairs each marker with the next on the same line, and wraps every text run between them so it never crosses a `<span>`, leaving a `<span>` that held part of a marker empty. An escape drops one backslash and is revealed as `&lt;&#94;&gt;`, which a second pass leaves alone. `expand_source` is the CLI pre stage: it wraps a same-line prose pair in one `<mark>`, code spans included, only outside fenced code (via `_fences`) and indented code; it reads the prose through `map_prose(skip_inline_code=False)` and finds the spans with `_fences.find_inline_code_spans` (a span may hold a line end, never a blank line, and a line end inside one does not end the line), and a marker inside a span stays literal for `apply_html`. The `\<^>` backslash escape renders a literal marker in both stages: `expand_source` reads the backslashes before a prose marker by parity, and for an odd run (an escape) adds one backslash and writes the marker's `<` as `&lt;`, so Python-Markdown and a CommonMark renderer both hand `mw post` the escaped form; an even run leaves the marker live.

4. **Button and lightbox** follow the embed pattern: `expand_source` replaces a standalone `[button ...]` or `[lightbox ...]` line with an `<a class="mw-...">`, through `_render_match(line)`, with no `apply_html`. They take no options.

5. **Mermaid** is a fence-replacing pre stage. It finds closed `mermaid` fences with `_fences.find_fenced_blocks` and emits a raw `<pre class="mermaid">` inline in `mw pre`, built from the `PRE_OPEN` constant the icons stage also reads, with the fence's indentation before every line and a blank diagram line left empty. So an indented fence keeps its indentation inside the `<pre>` unless the renderer strips it with the list item around the fence (spec.md's Mermaid entry supports the top level only). In-process a fence indented fewer than four columns, one under a list item included, is emitted the same way, inline at the 45 preprocessor, so it renders as `mw pre` output does through Python-Markdown, beside any text line. A fence indented four or more columns (to `_fences`, a fence under a list marker line or in a block opener's body) would be wrapped in `<p>`, split at a blank line, or hit the whitespace normalizer (30), which strips a stash placeholder's markers, so the 45 preprocessor replaces it with a line holding a random token and `MermaidStashPreprocessor` (26, below `normalize_whitespace` at 30 and above `html_block` at 20) stashes the `<pre>` at the same indentation, with the exact diagram text. It runs at 45, ahead of fence and superfences, so a `custom_fences` mermaid entry is inert.

6. **Icons** is a pre stage over `_fences.map_prose` (so fenced code, indented code, inline code spans, and HTML tags are skipped) plus an InlineProcessor (85) in-process. The pre stage runs at 5, after every directive stage, and passes `skip_blocks_opened_by=mermaid.PRE_OPEN` so a diagram the mermaid stage emitted keeps its text, since in-process it is stashed (by the 26 preprocessor or by `html_block`) and never read; no other `<pre>` block is recognized, and a block an author wrote with that exact open tag is read the same way, through the first `</pre>` as a CommonMark renderer reads it (spec.md Icons records the Decision and its Known gap). `markwright` ships no icons: `packs` maps a prefix to an SVG directory, read and validated by `icons.read_options` (omitted is silent, empty warns, bad shape or directory raises `OptionError`). It uses a sentinel default like fence, and reads options in `extendMarkdown`.

7. **Grid and annotate** follow the fence marker-comment pattern through `_markers.py`: `expand_source` swaps `[grid]`, `[grid cards]`, or `[annotate]` for a versioned marker, and `apply_html` reads it back (strict pydantic payload, fail-soft skip reported under `--warn`), edits the list or the annotated block through `_html` spans, and removes the marker. Grid also owns block containers: a paired `[grid]` ... `[/grid]` wraps its blocks in a grid `<div>` (`mw-grid-block`/`mw-grid-end`), a `[card]` ... `[/card]` directly inside it becomes `<div class="mw-card">` (`mw-card`/`mw-card-end`), and `[grid N]` for 1 to 6 (the `cards` and count tokens in either order) emits `mw-grid-cols-N`; the cards class is `mw-grid-cards` (renamed from `mw-cards`) and the `mw-grid` payload carries `columns`. Grid pairs its containers through `_containers.scan_containers`; an unclosed `[card]`, a stray `[/card]` or `[/grid]`, or a `[card]` outside a grid stays literal and gains an inline `mw-grid-problem` marker, while an invalid `[grid ...]` is not an opener, so its own line stays literal with no report, its unpaired `[/grid]` is a stray closer and gains the marker, and a `[card]` under it is outside a grid and is reported once; an opener demoted by a stray `[/grid]` also stays literal with no report. Their `mw-grid`, `mw-grid-block`, `mw-grid-end`, `mw-card`, `mw-card-end`, and `mw-annotate` markers and the `mw-annotation-B-N` ids are public contracts, versioned like `mw-fence`; the `mw-grid-problem` marker carries a versioned payload (`version`, `line`, `directive`, `reason`) from `mw pre` to `mw post`, is listed in the grid page's Marker Contracts table, is reported under `--warn`, and is removed from the output by `apply_html`.

8. **Tabs** (`tabs.py`): `expand_source` swaps each `[tab NAME]` ... `[/tab]` of a run of consecutive tab blocks for an `mw-tab`/`mw-tab-end` marker pair, pairing through `_containers.scan_containers`; `apply_html` orders the markers by position, groups consecutive tabs into sets, and emits pymdownx `tabbed` alternate-style markup: `<div class="tabbed-set tabbed-alternate mw-tabs">`, one radio `<input id="mw-tab-S-T" name="mw-tab-S">` per tab (the first checked), a `tabbed-labels` div, and a `tabbed-content` div with one block per tab. The `mw-tab-` id prefix keeps the ids from colliding with pymdown-extensions' own `__tabbed_` ids. An unclosed `[tab]` or a stray `[/tab]` stays literal and gains an inline `mw-tab-problem` marker; an empty `[tab ]` is not an opener and stays literal with no report. The `mw-tab`/`mw-tab-end` markers, the `mw-tabs` class, and the `mw-tab-S-T` id scheme are public contracts, versioned like `mw-fence`; the `mw-tab-problem` marker carries a versioned payload (`version`, `line`, `directive`, `reason`) from `mw pre` to `mw post`, is listed in the tabs page's Marker Contracts table, is reported under `--warn`, and is removed from the output by `apply_html`.

markwright emits classes and markup only and ships no CSS, JavaScript, or icons; the docs site (`docs/stylesheets/extra.css`, `docs/javascripts/`, `docs/icons/`) is the worked host example.

## Code Conventions

The `python` skill's rules apply. Project-specific points and the deliberate exemptions:

- `__init__.py` only re-exports the public API (`Config`, `ConfigError`, `ConfigWarning`, `OptionError`, the three config functions, and `disallowed_environments`) with `__all__` (the skill's library carve-out); add nothing else to it
- Data shapes are frozen pydantic models (`model_config = ConfigDict(frozen=True)`). An import used only in a model's field annotations must stay a runtime import, since pydantic resolves annotations at runtime; mark it `# noqa: TC00x` with that reason
- **Exemption: RST docstrings** (`:param:`, `:returns:`, `:raises:`) instead of the skill's Google style, for consistency across every existing module; there are no doctests and MkDocs does not render docstrings
- **Exemption: Python-Markdown's API names** (`extendMarkdown`, `makeExtension`, `handleMatch`) carry a per-line `# noqa: N802` with the reason, never a config-level ignore
- The ruff, mypy, and justfile blocks are the skill's canonical ones, pasted verbatim; do not add per-repo rules or ignores
- Every source file starts with a 2-line `# ABOUTME:` comment and uses `from __future__ import annotations`
- **Descriptive variable names always**: single-letter variables are NEVER allowed (`line_index` not `i`, `label_match` not `m`, `mark_element` not `el`)
- A one-caller private helper must hold a genuinely separate concern (a grammar, a scanner, a validator); otherwise inline it
- No `assert` for narrowing in `src/`; restructure (walrus in the comprehension, yield pairs) instead
- HTML output of the eight ported extensions must match the do-markdownit reference format (see the HTML Output Contracts in `.ai-sessions/v1-init/plan.md`)
- **Config law** (also in `docs/config.md`, Config Rules): omitting a key means its default (for a list, no restriction); a list names exactly what it holds, so an empty allowlist allows nothing and an empty denylist removes nothing, and no list treats empty as "everything"; a setting that makes a feature a no-op is legal but emits `ConfigWarning` (via `warnings.warn`, never `logging` or `print`) naming the key and source; every option markwright defines is validated in `config.py` and in the extension. New options must follow it. A `None` value counts as omitted. Python-Markdown coerces a `None` config default through `parseBoolValue`, so an option that must tell omitted from empty uses a sentinel default (`fence._ALL_ENVIRONMENTS`) and reads options in `extendMarkdown`, never `__init__`, so `setConfig` after construction applies
- `mw` prints `ConfigWarning` as one `mw: warning:` stderr line via `cli._show_warning` inside `warnings.catch_warnings()` (other categories keep Python's format)
- The `mw-fence` marker payload and the `mw-embed` preview are public cross-tool contracts: changes are versioned and read fail-soft

## Testing Approach

- TDD: RED (failing test) then GREEN (minimal code) then REFACTOR.
- Unit tests are `tests/test_<module>.py`, class-grouped, against the public API only (no imports of private names). Exception: `_fences` (the CommonMark scanner), `_markers` (the marker-comment contract), and `_containers` (the container-pairing scanner) are self-contained algorithms with contracts of their own and are tested directly in `tests/test_fences_*.py`, `tests/test_markers.py`, and `tests/test_containers.py`; the fences and markers tests may import `_html.tokenize` to build their inputs, while `test_containers` scans raw source. `tests/test_html.py` imports `_html.apply_edits` for its overlap guard alone, since no public path can produce overlapping edits. Every other private module is covered through the stage functions. In-process behavior uses `render_*(source)` helpers; the pure stage functions are tested by calling `expand_source` / `apply_html` directly. Shared setup is a factory fixture in the module that uses it (`feed_stdin` in `test_cli.py`, `write_file` in `test_config.py`).
- CLI tests assert on `capsys` stderr; library warning tests use `pytest.warns`.
- `tests/test_roundtrip.py` is the safety net for the pure path: it asserts `run_post(stub_render(run_pre(doc)))` equals the in-process render, including a hypothesis property over random documents built from markwright's grammar.
- `tests/integration/` (marked `integration`) drives `mw pre | hugo | mw post` through a real Hugo build and installs the wheel in a clean venv. `just check` runs it; it skips when `hugo` or `mw` is not on PATH. Touching fence line-prefix or fence-scanning logic? Exercise it here (or the Chroma fixtures in `test_fence.py`): the in-process round-trip uses Pygments and will not catch Chroma-only bugs.
- Test our logic only; do not test Python-Markdown, pymdownx, argparse, or pygments behavior.

- `spec.md` (repo root): the living project spec in bpe's canonical sections, edited in place; its `## Roadmap / phase log` indexes the archives. Its `## Goals` is indexed by feature: a Feature Status table, the rules every feature follows, and one entry per feature. A sentence starting `Planned (ITEM):` is behavior a Roadmap Upcoming item will build, one starting `Known gap:` is where the code or the docs fall short, a `Today` sentence under a Planned one says what the code does until the item ships, and one starting `Decision (DATE):` records a departure from an earlier rule or from `do-markdownit`; a phase edits the entry of the feature it changes and never adds a section named for a release or an issue. The 0.4.0 fix plan (26 steps: the fixes the #30 spec reconciliation and the plan review found, the docs catch-up, and the Material mapping page) is archived in `.ai-sessions/fix-plan-0.4.0/`, the #30 cycle (containers: block grids, cards, and tabs) in `.ai-sessions/containers-30/`, both merged to `main` in PR #35 and released as 0.4.0; the finished #29 cycle (the 0.4.0 adversarial review fixes) is archived in `.ai-sessions/review-fixes-29/`, the #20 cycle (`mw pre` skipping directives inside fenced code) is archived in `.ai-sessions/fenced-directives-20/` and the 0.4.0 cycle (issue #16) in `.ai-sessions/material-parity-0.4.0/`. markwright is otherwise issue-driven, so run `/bpe:brainstorm` to promote a Deferred item into Goals before `/bpe:plan`.
- `plan.md` and `todo.md` (repo root): absent between cycles. `/bpe:plan` writes them for the next cycle, `/bpe:goal` runs them, and both are archived to `.ai-sessions/<slug>/` with an `accomplishment.md` when the run ends. A step clears the `Planned (ITEM):` sentences it ships, deletes their `Today` sentences, and deletes the Roadmap Upcoming line it ships. A release (version bump, dependency floors, CHANGELOG date, tag, GitHub Release) is never a plan step, since `pyproject.toml`, `uv.lock`, and the workflows are outside the spec's `paths:` fence; it is done by hand around the merge.
- `.ai-sessions/config-system/{spec,plan,todo,accomplishment}.md`: the **completed** 0.2.0 config cycle (shipped in #10). The config schema, discovery, and precedence now live in `docs/config.md`.
- GitHub issues drive work since 0.2.0 (0.3.0 was issues #11 and #13 plus the skill 2.0 audit). `CHANGELOG.md` records each release.
- `.ai-sessions/v0.1-remediation/{spec,plan,todo,accomplishment}.md`: the **completed** step-55 remediation (R1 through R11, shipped as 0.1.0). `accomplishment.md` is the durable record; the marker contract and parity Decisions (D1, D2, D3) live in its `spec.md`.

- `.ai-sessions/`: session summaries (read the most recent for context). `.ai-sessions/lessons.md` accumulates cross-session lessons.
